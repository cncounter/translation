## 4.10. Verification of `class` Files

## 4.10. class 文件的校验

尽管 Java 编程语言的编译器必须只生成满足前面各节所有静态和结构约束的 `class` 文件，但 Java 虚拟机无法保证它被要求加载的任何文件都是由该编译器生成的，或者是格式正确的。像 Web 浏览器这类应用并不会下载源代码再去编译，它们下载的是已经编译好的 `class` 文件。浏览器需要判断这个 `class` 文件是由可信的编译器生成的，还是由试图利用 Java 虚拟机的攻击者生成的。

编译期检查还面临另一个问题: 版本偏差(version skew)。用户可能成功地将一个类(比如 `PurchaseStockOptions`)编译为 `TradingClass` 的子类。但是自该类编译之后，`TradingClass` 的定义可能已经以与既有二进制不兼容的方式发生了改变。方法可能被删除，或其返回类型、修饰符发生了改变。字段可能改变了类型，或从实例变量变成了类变量。方法或变量的访问修饰符可能从 `public` 变成了 `private`。关于这些问题的讨论，请参见 *The Java Language Specification, Java SE 8 Edition* 第 13 章 "Binary Compatibility"。

由于存在这些潜在问题，Java 虚拟机需要自行校验它试图纳入的 `class` 文件确实满足所需的约束。Java 虚拟机实现在链接时([§5.4](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-5.html#jvms-5.4))校验每个 `class` 文件是否满足必要的约束。

链接期校验可以提高运行时解释器的性能。那些原本要在运行时对每条被解释指令执行的、代价高昂的约束检查可以由此消除，Java 虚拟机可以假定这些检查已经执行过了。例如，Java 虚拟机将已经知道以下事项:

- 操作数栈不会上溢或下溢。
- 所有局部变量的使用和存储都是合法的。
- 所有 Java 虚拟机指令的参数都具有合法类型。

Java 虚拟机实现可以采用两种校验策略:

- 对于版本号大于或等于 50.0 的 `class` 文件，必须使用类型检查校验(verification by type checking)。

- 对于版本号小于 50.0 的 `class` 文件，所有 Java 虚拟机实现都必须支持类型推断校验(verification by type inference)，但符合 Java ME CLDC 和 Java Card 规范的实现除外。

  在支持 Java ME CLDC 和 Java Card 规范的 Java 虚拟机实现上，校验由其各自的规范来规定。

在这两种策略中，校验主要是针对 `Code` 属性([§4.7.3](#jvms-4.7.3))的 `code` 数组，强制执行 [§4.9](#jvms-4.9) 中的静态和结构约束。不过，在 `Code` 属性之外，校验期间还必须执行三项额外的检查:

- 确保 `final` 类不会被继承。
- 确保 `final` 方法不会被重写([§5.4.5](https://docs.oracle.com/javase/specs/jvms/se8/html/jvms-5.html#jvms-5.4.5))。
- 检查每个类(除 `Object` 外)都有一个直接父类。
